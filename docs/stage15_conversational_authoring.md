# 阶段 15：对话式补全世界

m09500 需求 ③ 的落点：玩家用一句话不断把世界补全，而不是每次打开表单填字段。

## 一、这条通道能改什么、不能改什么

| | 可以 | 不可以 |
| --- | --- | --- |
| 世界文档 | 新增地点、物品、门、实体、事件、任务 | 改权威游戏状态 |
| 知识库 | 新增知识条目（含 `set_note` 转成的设定） | 改已有条目的内容 |
| 战役状态 | 无 | 任何字段 |

模型只输出「操作提案」，从不宣布改动已完成。提案在**世界文档副本**上逐条应用，
每条都走 `world_editor` 的校验读改写，所以一条会让引用悬空的操作会被当场拒绝，
并在 `warnings` 里说明原因（例如 `door 'ghost_door' requires unknown key item 'nope'`）。

## 二、两段式：先提案，再提交

1. `POST /api/v1/worlds/{world_id}/authoring/propose`——给一句话，返回：
   - `reply`：给作者看的一句回复；
   - `ops`：通过校验的操作摘要；
   - `changes`：地点/物品/门/实体/事件/任务的数量前后对比；
   - `knowledge_titles`：将新增的知识标题；
   - `warnings`：被拒绝或被跳过的部分及原因；
   - `empty`：没有任何可执行改动时为 true。
   此时**没有任何写入**。
2. `POST /api/v1/worlds/{world_id}/authoring/commit`——把作者确认后的提案交回来。
   服务端不信任客户端回传的数据：世界部分重新按 `WorldDefinition` 解析并再次做引用校验，
   知识条目重新按 `KnowledgeEntryCreate` 校验，任一项不合法返回 400。

提交只做两件事：保存世界文档（引用校验通过才保存）、写入知识条目。
知识写入失败只影响那一条，其它照常写入并在 `warnings` 里报告。

## 三、为什么不做成「模型直接改世界」

- 模型的错误会变成一个看似合理但引用悬空的配置，直到玩家走进那扇门才炸。
- 先提案再提交，作者在写入前就能看见「地点 3 → 4」「知识：River」。
- 拒绝是可读的：`add_door 未通过校验：door 'ghost_door' requires unknown key item 'nope'`。
  这句话直接来自真实校验代码，不是模型编的解释。

## 四、提示词里给了什么

`build_prompt` 会附上当前世界的**已有 id 清单**（地点、物品、门、实体、事件、任务、知识标题）
和最近 12 轮对话。这样模型更容易复用已有 id 而不是另起一套命名，
也避免它把已经存在的地点再加一遍——真正重复时由 `_with_id` 拒绝。

## 五、前端入口

`frontend/src/components/WorldStudio.jsx` 新增「对话补全」页签（共 12 个页签）：
对话记录、输入框（Enter 发送）、待确认卡片（操作列表 + 数量对比 + 被拒绝的原因）、
「确认写入」与「丢弃」两个按钮。写入成功后自动重新载入世界。

## 七、已知限制

- 只能「新增」，不能改已有地点/物品/门的字段，也不能删除。
- 提案不包含故事线节点；故事线仍由「剧本生成」负责。
- 对话历史只保留最近 12 轮进提示词，`history` 最多 40 条。
- 模板叙事、无模型环境下该页签返回 503，不会静默失败。

## 八、本地验证

1. 配好任意一个模型供应商或本地模型。
2. 世界工作台 → 对话补全 → 输入「在广场东边加一条通往河边的小路，并写一条关于这条河的设定」。
3. 检查待确认卡片：地点数量应从 N 变成 N+1，知识 1 条。
4. 点「确认写入」，世界地图页签里应出现新地点；取消勾选前的任何游戏状态都不变。
